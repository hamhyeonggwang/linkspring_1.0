# 기존 UI/UX 복원 및 기관 CSV 호환성 수정 설계

상태: 설계안. 앱 코드·DB·설치파일에는 아직 적용하지 않음.

## 1. 목표와 기준

기존 업무 화면과 기관의 익명 CSV 양식을 기준으로 앱을 맞춘다. Windows 로컬 설치형 배포, SQLite 저장, 백업·복원은 유지한다. 사용자가 새 CSV 양식으로 매번 재작성하거나 앱 전용 가명 ID를 직접 만들어야 하는 동선을 없앤다.

UI 기준은 Git 이력에서 확인한 `155bdac`의 치료 현황판이다. 사용자가 선호하는 기존 화면의 구조가 코드에 남아 있다. 이 버전의 화면·동선은 복원하되, 과거의 고정 날짜·추정값 자동 확정·이름/생년월일 기반 ID 생성·저장 실패 후 성공처럼 보이는 동작은 복원하지 않는다. 현재 데이터 검증, 충돌 방지, 저장 확인은 유지한다.

현재 설치본 기준은 `8d4e53a`이다. 메뉴·일정표·CSV 요구 형식 변경은 데스크톱 포장 이전 `ea93a8d`의 업무 흐름 재작성에 이미 들어갔고, 데스크톱 포장은 해당 화면을 그대로 사용했다. 로컬 프로그램의 기술적 제약으로 화면을 바꿀 필요는 없다.

## 2. 확인된 원인과 미확인 사항

| 항목 | 기존 코드 | 현재 코드 | 수정 방향 |
| --- | --- | --- | --- |
| 일정 메뉴 | 치료 일정 | 서비스 일정 | 치료 일정으로 복원 |
| 일정표 행 | 치료사별 한 행 | 예약 회기별 한 행 | 치료사별 현황판 복원 |
| 일정표 열 | 08:30~17:30 시작 시각, 30분 단위·점심 제외 | 날짜·시간·서비스·담당자 코드·회기 상태 | 시간 열과 예약 코드 셀 복원 |
| 일정 확인 | 전체 일정 / 빈 회기만 보기, 범례, 치료사·예약 건수 | 목록 중심 | 기존 필터·범례·요약 복원 |
| 대기자 목록 | 가명 ID·치료 유형·가능 시간·대기 시작일·최근 연결·수정 | 가명 ID·서비스·가능 시간·대기 시작·상태·수정 | 기존 열 순서·최근 연결 복원, 상태는 부가 표시 |
| 대기자 CSV | 기관 행의 정해진 위치를 읽어 ID 생성 | 지정된 7개 열 제목과 ID 정규식 요구 | 기관 양식 어댑터와 안정적인 내부 ID 연결 |
| 데스크톱 조작 | 기존 공통 헤더·메뉴 | 별도 상단 도구막대·매 실행 안내창 추가 | 기존 프레임에 필요한 기능 통합 |

현재 `lib/csv.ts`의 `participantImport()`는 `가명 ID`, `치료`, `대기 시작일`, `희망 날짜`, `오전`, `오후`, `상태`라는 정확한 열 제목을 요구한다. `lib/domain.ts`의 `aliasSchema`는 `아동-` 또는 `대기자-` 뒤에 대문자 영문·숫자 4~32자가 있는 값만 허용한다. 따라서 이미 익명 처리된 코드도 열 제목이나 코드 모양이 다르면 실패한다. 정규식 통과 여부는 개인정보 익명 처리 여부를 판별하지 못한다.

행 데이터 검증 실패 시에도 현재는 가명 ID·날짜·서비스·상태를 한 메시지로 묶어 안내한다. 실제 문제가 날짜나 상태여도 사용자는 ID 문제로 이해할 수 있다.

치료 현황판 가져오기는 현재도 `legacyScheduleImport()`가 있지만, 고정된 열 위치·08:00 시작 10분 간격 추정·담당자/예약 코드의 제한된 문자 형식·한 날짜만 허용하는 제약이 있다. 공통 CSV 파서는 중복 열 이름과 행별 열 개수 차이를 거부한다. 이 제약들도 기관의 익명 현황판과 충돌할 수 있다.

사용자가 열 제목을 확인하고 대기명단 양식을 정정했다. 최종 대기명단은 `타임스탬프, 아동이름, 아동 생년월일, 보강치료 희망 날짜, 치료, 오전, 오후, 비고`다. 앞서 제시한 차트번호·주소·보험 등이 포함된 명단은 이번 구현 기준에서 제외한다.

이 대기명단에는 현재 코드가 필수로 요구하는 `가명 ID` 열이 없다. 따라서 현재 `participantImport()`에서는 값의 익명 처리 여부를 확인하기 전에 `필수 열이 없습니다: 가명 ID` 오류가 발생하는 것을 헤더 수준에서 확인할 수 있다. 다른 필수 열인 `대기 시작일`, `희망 날짜`, `상태`도 이 기관 양식과 직접 일치하지 않는다.

실제 파일의 값·구분자·익명 표시 방식과 치료 시간 열은 아직 확인하지 않았다. 헤더 호환 문제는 확인됐지만 실제 파일 전체에 대한 재현·수정 검증은 남아 있다. 실명·연락처·생년월일 원본을 요청하지 않고 가상 예시로 검증한다.

## 2-1. 확정된 기관 열 대응

### 익명 치료사 시간표

확인된 앞 7개 열: `Unnamed, 일자, 요일, 부서, 아이디, 치료사, 건수`.

| 원본 열 | 처리 |
| --- | --- |
| Unnamed | 내보내기용 인덱스 열로 취급하고 업무 데이터에서 제외. 이 프로필의 첫 머리글이 공란이거나 `Unnamed: 0`인 변형도 지원 |
| 일자 | 시간표 날짜로 읽고 정규화 |
| 요일 | 표시 참고값. 일자로 계산한 요일과 다르면 미리보기에서 안내 |
| 부서 | 확인된 기관 대응표를 통해 치료 종류로 연결 |
| 아이디 | 기관의 안정적인 익명 치료사 코드로 내부 ID와 연결. 앱 전용 코드 모양을 요구하지 않음 |
| 치료사 | 익명 처리된 치료사 표시명으로 현황판 행 머리글에 사용 |
| 건수 | 원본 건수와 해석한 예약 수를 대조하는 참고값. 시간 열로 읽지 않음 |
| 이후 열 | 시간별 예약 셀. 실제 시간 헤더와 예약 표기 방식을 확인한 뒤 변환 규칙 확정 |

앞 7개 열만으로 시간별 예약을 재구성할 수는 없다. `건수` 뒤의 열을 근거 없이 08:00부터 10분 간격으로 단정하지 않는다. 행은 치료사, 열은 시간이라는 기존 현황판 구조는 유지한다.

### 대기명단 — 사용자 최종 정정 양식

```csv
타임스탬프,아동이름,아동 생년월일,보강치료 희망 날짜,치료,오전,오후,비고
```

| 원본 열 | 처리 |
| --- | --- |
| 타임스탬프 | 보강 신청 접수 시각으로 저장. 날짜 순위를 계산할 때는 ‘신청일 기준’임을 표시하고 기관의 최초 대기 시작일과 구분 |
| 아동이름 | 익명 처리된 표시값을 읽어 기존 익명 코드와 내부 ID 연결. 새 `가명 ID` 열을 요구하지 않음 |
| 아동 생년월일 | 양식 인식은 허용하되 매칭·ID 생성·저장에는 사용하지 않음. 빈 값이어도 이것만으로 가져오기를 거부하지 않음 |
| 보강치료 희망 날짜 | 날짜별 희망 일정으로 정규화 |
| 치료 | 치료 종류로 연결. 복수 치료는 확인된 표기로 분리·정규화 |
| 오전 | 오전 희망 시각 또는 시간 범위로 읽음 |
| 오후 | 오후 희망 시각 또는 시간 범위로 읽음 |
| 비고 | 확인된 상태 표기를 미리보기에서 제안. 자유 서술 원문은 저장하지 않으며 모호한 내용은 담당자가 상태를 선택 |

이 양식에는 희망 날짜와 오전/오후가 있으므로 **별도로 가능 시간을 다시 입력하도록 요구하지 않는다.** 명단과 희망 일정을 한 번의 가져오기로 함께 반영한다. 오전·오후가 모두 비어 있거나 해석할 수 없는 행만 미리보기에서 해당 시간을 확인하도록 한다.

헤더의 BOM과 앞뒤 공백을 정리한 뒤 이 8개 열을 이름으로 연결한다. 원본 열 순서를 바꾸거나 `희망 날짜`, `상태`, `대기 시작일`로 이름을 바꿀 필요가 없게 한다. 재내보내기에서 인덱스 공란 열이 추가돼도 확인된 프로필에 한해 그 열을 무시한다.

익명 처리된 `아동이름` 값이 파일을 다시 만들어도 유지되고 사람별로 구별된다면 이를 출처별 식별 키로 사용할 수 있다. 같은 익명 표시가 여러 사람에게 쓰이거나 매번 변경되는 경우에는 안정적인 연결이 불가능하므로 해당 항목만 검토하도록 한다. 행 번호나 생년월일 해시로 이를 임의 해결하지 않는다.

`비고`의 빈 값은 새 보강 신청에서 `처리 대기` 제안으로 표시한다. 기존 신청을 다시 읽을 때 빈 비고로 연결·안내·취소 등 이미 처리된 상태를 덮어쓰지 않는다. ‘취소’, ‘완료’ 같은 단어가 포함됐다는 이유만으로 상태를 확정하지 않고, 확인된 표현과 문맥 또는 담당자의 선택으로 반영한다.

## 3. 화면 복원 설계

### 치료 일정

- 메뉴명과 제목을 `치료 일정`, `당일 치료 일정`으로 복원한다.
- 행은 치료사, 열은 시간, 셀은 예약 코드/회기 상태로 표시한다. 날짜는 표 위에서 선택한다.
- 원본 또는 저장된 기관 설정의 치료사 순서를 유지하고, 열은 시간순으로 정렬한다. 치료사 수는 14명으로 고정하지 않는다.
- 치료사 머리글과 시간 머리글을 고정하고 가로 스크롤을 지원한다. 열 개수는 실제 시간 목록에서 계산한다.
- 예약, 결석으로 발생한 빈 회기, 연결 완료, 미배정을 색상과 문구로 구분한다. 빈 셀을 결석으로 자동 해석하지 않는다.
- 예약 셀 선택 → 예약 상세 및 결석 등록 → 빈 회기 셀 선택 → 후보 확인 → 연결 확정 → 안내 기록의 흐름으로 이어진다.
- `전체 일정 보기 / 빈 회기만 보기`, 날짜별 치료사·예약 건수, 상태 범례를 복원한다.
- 일치 판정에는 날짜·내부 치료사 ID·시작 시각을 모두 사용한다. 다른 날짜의 빈 회기가 같은 셀에 섞이지 않도록 한다.
- 직접 일정 등록 기능은 치료 일정 화면의 보조 버튼으로 배치한다.

### 대기자 관리와 공통 프레임

- 기존 표의 항목과 순서를 복원한다. CSV에 들어 있던 익명 코드는 대기자 식별 표시값으로 유지한다. 내부 시스템 ID는 기본 화면에서 숨긴다.
- `CSV 불러오기 → 미리보기 → 반영`의 기존 짧은 동선을 유지한다. 알려진 기관 양식에 불필요한 열 연결 절차를 반복하지 않는다.
- 활성/중지 상태는 기존 열을 대체하지 않고 배지나 수정창에서 제공한다.
- 별도 데스크톱 상단 도구막대는 기존 설정/도움말 메뉴에 통합한다. 실제 업무·체험 구분은 작은 상태 표시로 남긴다.
- 시작 안내는 첫 실행 또는 도움말 선택 때 표시한다. 매 실행마다 업무 화면을 가리지 않는다.
- 치료 외 사회사업으로의 확장성은 내부 데이터 구조와 기관별 표시 문구 설정으로 확보한다. 이번 기관의 화면에는 기존 치료 용어를 사용한다.

## 4. CSV 호환 계층

처리 순서: 로컬에서 파일 읽기 → 양식 판별 → 열/값 정규화 → 식별 코드 연결 → 업무 규칙 검증 → 변경 미리보기 → 한 트랜잭션으로 반영.

### 지원할 입력 형식

1. 기관의 익명 치료 현황판 CSV: 현재 사용하는 가로 시간표를 그대로 입력한다.
2. 기관의 익명 대기 신청 CSV: 위에서 확정한 8개 열의 양식을 그대로 입력한다.
3. 기존 앱 표준 CSV v1: 이미 만든 파일은 계속 지원한다.
4. 알려지지 않은 변형: 가져오기 창 안에서 열 연결을 한 번 확인하고, 기관 양식 프로필로 로컬 저장한다. 다음에는 같은 양식에 재사용한다.

기관 대기 신청 프로필에서는 `아동이름`이 익명 표시 열이라는 전제로 연결하되, 헤더만으로 값의 익명 처리 여부나 고유성을 보장한다고 간주하지 않는다. 표준 v1은 기존 `가명 ID`를 계속 지원한다. 다른 기관의 `익명 ID`, `대상자 코드` 등의 이름은 추가 열 연결 후보로 제시한다. 필요한 열만 반영하고 불필요한 열과 원문 메모는 저장하지 않는다.

### 식별 코드

- CSV의 외부 익명 코드와 앱의 내부 ID를 분리한다. 기존 `아동-...`, `대기자-...` 내부 ID는 유지해 저장된 연결 이력을 보존한다.
- 새 외부 코드가 들어오면 내부 ID를 생성하고 `가져오기 출처 + 외부 익명 코드 → 내부 ID` 관계를 저장한다. 같은 출처·코드의 재가져오기는 같은 대기자를 갱신한다.
- 코드의 앞자리 0, 하이픈, 대소문자는 원본 의미를 보존한다. 코드 형식만 맞추려고 숫자 변환하거나 대문자로 일괄 변경하지 않는다.
- 치료사·예약 코드도 화면 표시값과 내부 식별값을 분리해 같은 방식으로 호환한다. 후보 매칭과 중복 방지는 내부 ID로 처리한다.
- 기존 표준 ID와 이미 저장된 대기자는 그대로 연결한다. 기존 기록과 다른 외부 코드를 대응시켜야 한다면 사용자가 연결 대상을 검토하도록 하며, 유사한 문자열만으로 자동 병합하지 않는다.
- 익명 처리와 고유 식별은 별개다. 여러 사람이 모두 `김**`처럼 같게 표시되어 구별할 수 없다면 이름이나 행 번호를 기준으로 합치지 않는다. 기존의 안정적인 익명 코드 열을 선택하거나 중복 후보를 검토하도록 안내한다. 안정적인 코드가 없는 파일의 반복 반영을 자동으로 동일인 처리한다고 약속하지 않는다.
- 가명 코드는 기관의 기존 코드로 충분하다. 사용자가 앱 전용 접두어를 추가해야 하는 요구는 없앤다. 실명·생년월일을 복원하거나 그 조합을 다시 해시하는 방식도 사용하지 않는다.

### 날짜·시간·상태

- 기관 양식에서 확인한 날짜 표기(예: `2026. 9. 17.`)를 내부 날짜로 명확하게 정규화한다. 원본 값과 변환 결과는 미리보기에서 비교할 수 있다.
- 이번 대기 신청 프로필의 `타임스탬프`는 신청 접수일이다. 보강 신청일 기준 정렬에 사용할 경우 그 기준을 화면과 미리보기에 명시한다. 기관 최초 대기 시작일이 필요한 업무라면 별도 입력/연계를 지원하고, 희망 날짜나 오늘 날짜를 대기 시작일로 조용히 대체하지 않는다.
- 치료 종류의 약칭, 오전/오후 시간 표현, 상태 값은 확인된 대응표로 변환한다. 모르는 값은 확인 필요로 표시하며 치료 종류를 추정하지 않는다.
- 현황판 시간은 실제 시간 헤더나 검증된 기관 프로필로 해석한다. 10분 칸 3개에 같은 예약이 반복된 경우와 시작 칸에만 예약을 적는 경우를 구분한다. 동일 코드가 이어진다는 이유만으로 별개 회기를 합치지 않는다.
- 현재 30분 회기 규칙은 유지한다. 맞지 않는 행·셀은 위치와 이유를 보여 준다. 예전 코드처럼 조용히 제외하지 않는다.
- 여러 날짜가 있는 시간표는 날짜별 건수와 반영 대상을 미리보기에서 선택한다. 첫 날짜만 몰래 반영하거나 파일을 수동 분할하도록 일괄 요구하지 않는다.
- 비어 있는 머리글·중복 시간 머리글 등의 처리는 해당 현황판 프로필에서 의미가 확인된 경우에 한해 지원한다. 열 수 차이가 생겼을 때 앞뒤 열이 잘못 연결되는 느슨한 파싱은 피한다.

### 오류와 반영 정책

- 짧은 팝업 하나로 종료하지 않고 기존 미리보기 창에 `행 번호 / 열 / 문제 / 수정 방법`을 표시한다. 실제 식별정보가 의심되는 원문 값은 오류 로그에 남기지 않는다.
- 예: `가명 ID 필요` 대신 `대기자를 구별하는 익명 코드 열을 선택해 주세요`.
- 예: `가명 ID·날짜·서비스 확인` 대신 `8행 ‘희망 날짜’: 날짜로 해석할 수 없습니다`.
- 새 등록·갱신·중복·확인 필요·날짜별 건수를 표시한다. 오류가 있으면 저장 전 수정/확인하도록 한다.
- 기본 반영은 선택한 범위 전체 성공 또는 전체 취소다. 중복·검증 오류가 있는 행을 사용자에게 알리지 않고 누락시키지 않는다.
- 재가져오기에서 중지된 대기자가 자동 활성화되지 않도록 하고, 신청 상태와 대기자 활성 상태를 분리한다.
- CSV를 AI API에 전송하지 않는다. 가져오기와 형식 변환은 로컬에서 수행한다.

## 5. 저장소와 수정 대상

현재 SQLite 데이터와 감사 이력은 유지한다. 외부 코드 대응표, 표시값, 기관 양식 프로필, 필요한 표시 순서 메타데이터만 추가 마이그레이션으로 도입한다. 가져오기 중 코드 대응과 업무 데이터 반영은 같은 트랜잭션에 포함한다. 실패한 미리보기 때문에 빈 대기자나 대응표만 남지 않도록 한다.

| 파일/영역 | 예정 변경 |
| --- | --- |
| `app/page.tsx` | 기존 치료 현황판·대기자 표·업무 동선 복원, 기관 코드 표시 |
| `app/globals.css` | 남아 있는 현황판 스타일 재사용, 동적 시간 열·고정 머리글 |
| `renderer/main.tsx`, `renderer/desktop.css` | 데스크톱 도구를 기존 프레임에 통합, 첫 실행 안내 |
| `lib/csv.ts` | 양식 판별·기관 어댑터·정규화·구체적인 검증 오류 |
| `lib/domain.ts` | 외부 표시 코드와 내부 ID 구분, 기존 업무 검증 유지 |
| `lib/state-actions.ts`, `lib/state-store.ts` | 안정적인 재가져오기, 활성 상태 보존, 새 메타데이터 읽기/쓰기 |
| `drizzle/` 추가 마이그레이션 | 코드 대응표·표시값·가져오기 프로필·순서 저장 |
| `desktop/database.ts` | 이전 버전 백업의 스테이징 업그레이드 및 복원 검증 |
| `docs/전처리_CSV_연계규격_v1.md` 및 신규 호환 안내 | v1 유지, 기관 CSV 직접 수용 규칙 추가 |
| CSV/업무/데스크톱 테스트 | 대표 기관 양식·기존 파일·재가져오기·업데이트 보존 검증 |

현재 복원은 스키마가 완전히 같은 백업만 허용한다. 마이그레이션이 추가되면 1.0.0 백업도 복원 가능하도록 신뢰된 구버전 스키마/마이그레이션을 검증하고, 임시 DB에서 업그레이드·검증한 후 교체하는 절차가 필요하다. 복원 전 자동 백업은 계속 보존한다.

## 6. 작업 순서와 완료 기준

1. 확정된 기관 헤더로 필수 열 오류를 재현한다. 가상 값으로 된 익명 코드·날짜·치료·비고 예시와 `건수` 뒤 시간 열을 확인해 값 변환 및 재가져오기 규칙을 검증한다. 헤더 대응 확정과 실제 파일 검증 완료를 구분한다.
2. `155bdac`의 화면을 기준으로 치료 현황판과 대기자 표, 공통 동선을 복원한다. 기존 표시 방식과 현재 정확한 업무 로직을 결합한다.
3. 기관 CSV 어댑터와 내부 ID 연결·저장 마이그레이션을 함께 구현한다. 오류는 미리보기에서 해결할 수 있도록 한다.
4. 대표 CSV로 예약 위치, 치료사 수, 대기자 수, 희망 날짜·시간·상태를 원본과 대조한다. 같은 파일을 두 번 읽어도 대상자와 신청이 늘지 않아야 한다.
5. 행 순서를 바꾼 파일, 앞자리 0이 있는 코드, 같은 코드의 여러 희망 날짜, 익명 표시 중복, UTF-8 BOM/EUC-KR, 10분 칸의 반복 예약, 불명확한 상태를 검증한다.
6. 현황판에서 결석 등록 → 후보 확인 → 연결 확정 → 안내 기록, 재시작 유지, 갱신 충돌 거부를 확인한다. 동일한 화면 구성으로 웹 개발 화면과 데스크톱 화면을 비교한다.
7. 기존 1.0.0 DB와 백업이 보존·업그레이드되는지 확인한 뒤 Windows 수정 설치본을 새 버전으로 만든다. 이전 `.exe`와 체크섬은 보존한다. Windows 실제 설치 검증 여부를 결과에 명시한다.

완료 판정의 핵심은 **기관 CSV의 열 이름과 익명 코드를 사용자가 다시 작성하지 않아도 불러오고, 익숙한 치료사 × 시간 현황판에서 같은 업무를 수행할 수 있는가**이다.
